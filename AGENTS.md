This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Node Version Management

Node version is managed via `fnm` and automatically loaded across shells via `~/.zshenv` to match `package.json` (`devEngines.runtime.version`, e.g. `24.21.0`).

## Commands

This project uses `pnpm`. Use `pnpm` and `pnpm dlx` for package execution:

```bash
pnpm expo install <package>  # ALWAYS use instead of pnpm add — resolves SDK-compatible versions
pnpm expo start              # start the dev server
pnpm expo lint               # lint
pnpm tsc --noEmit            # typecheck
pnpm format:check            # check formatting
pnpm test:e2e                # E2E functional tests
pnpm test:visual             # visual regression tests (Chromatic)
pnpm dlx expo-doctor         # diagnose dependency and config issues
pnpm expo install --fix      # fix incompatible package versions
```

### Verification Guidelines

- **Always run**: `pnpm tsc --noEmit`, `pnpm expo lint`, and `pnpm test:e2e` before declaring any task done.
- **Check the demo profile**: open the screens you changed with the demo profile (see **Demo Profile** below) and keep them presentable.
- **Always update the changelog**: before declaring any task done, check that every user-facing change has its changie fragment (see **Changelog Fragments** below). A task is not done without it. Never declare completion when `pnpm web` or dev server is broken.
- **Visual Tests (`pnpm test:visual`)**:
  - You **MUST** write visual tests for new views.
  - Visual tests for that view **MUST** be collocated next to the view inside `src/features/<feature>/` and named accordingly (e.g. `src/features/<feature>/<view-name>.visual.ts`).
  - You **MUST NOT** write a new test if an existing visual test covers the changes/new additions.
  - You **MUST** call out new visual tests that will be added or ones that you expect to be affected if none will be added.
  - ONLY run if you update or alter the UI (screens, components, styles, themes). Do NOT re-run visual tests for non-visual changes (e.g. typing comments, types, config files that don't alter CSS).
  - Chromatic bills per snapshot. A commit that cannot change how the app looks (CI workflows, tooling, docs) adds a `Chromatic: skip` trailer to its message. When every non-merge commit on a branch has it, CI skips the visual tests, and Chromatic marks the commit as passing without taking snapshots, so its required checks stay green, and merging it to `main` publishes no new baseline. One commit without it runs Chromatic as usual. Never add it to a commit that touches app code, styles or visual tests.
  - Visual tests **MUST NOT** contain assertions (`expect(...)`). They should strictly navigate, prepare UI state, and call `takeSnapshot()`. All functional assertions belong in E2E tests (`*.e2e.ts`).
- **E2E Tests (`pnpm test:e2e`)**:
  - You **MUST** write E2E tests for new views and user flows.
  - E2E tests for that view **MUST** be collocated next to the view inside `src/features/<feature>/` and named accordingly (e.g. `src/features/<feature>/<view-name>.e2e.ts`).
  - Tests **MUST** be updated if possible to keep testing succinct.
  - Implementation plans **MUST** describe new E2E tests that will be written.
  - Run when modifying user flows, interactions, or data persistence. Do not re-run for comment/type-only changes.
  - Keep the suite fast; it is CPU-bound and each worker boots the app once and resets it in place before every test. Seed with the seed helpers, navigate with `openRoute`, and never `page.goto`/`page.reload` unless loading or restarting is what the test checks. Extend a feature's add → view → edit → delete journey with `test.step` instead of adding tests that seed the same record. Test behaviour owned by a shared component once. Wait for state, never for time. Opt out of the shared app (`freshApp`) only for tests about loading, other tabs or legacy schemas. Details: `.agents/skills/testing-workflow/SKILL.md` ("Keeping the E2E Suite Fast").
- **Fix Failing and Flaky Tests as You Meet Them**: Every failing test you encounter is yours to fix in the current change, including ones unrelated to it (lint, typecheck, E2E or visual). Never settle for a rerun that passes, and never skip, disable, quarantine or loosen a test to get green. "Flaky" is not a root cause: reproduce the failure (rerun it repeatedly, under the full suite's load if it only fails there), find why it fails, and fix the test or the app code so it passes reliably. If you cannot reproduce or fix it, say so in your summary with the failing output and what you tried.

## Navigation & Routing

- Views, view-specific subcomponents, and their tests live in `src/features/<feature>/`. Do NOT put non-route code, subcomponents, or tests inside `app/` (Expo Router scans `app/` for routes, and Metro will crawl test dependencies like Playwright if placed there).

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `pnpm expo run:ios|android` locally, or `pnpm dlx eas-cli build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md
- **No Advertising ID**: Never add a package that uses the Android advertising ID or declares `com.google.android.gms.permission.AD_ID`, directly or through its dependencies (e.g. ads, analytics, attribution or Firebase Analytics SDKs, `play-services-ads`, `play-services-ads-identifier`). Healthy's Play Console declaration says it doesn't use an advertising ID. Before adding a native dependency, check that its manifest and transitive dependencies don't pull these in. After building, confirm the merged manifest has no `AD_ID` permission.
- **Component Reuse**: Always prioritize reusing existing UI components (e.g. pickers, buttons, pills, modals) before creating new ones. In implementation plans, explicitly audit and suggest existing components to be reused beforehand. Never copy-paste styles across files: if styles are only used in one place, they can be written in that place, but when they need to be reused, extract a separate reusable component.
- **Component & Test Collocation**: Views, view-specific components (e.g. `ConditionForm`, `LabResultForm`), and their E2E and visual tests **MUST** be collocated in feature folders inside `src/features/<feature>/` (e.g. `src/features/conditions/`). ONLY components that are genuinely shared across multiple features live in `src/components/`. The `app/` directory is strictly reserved for thin route definitions.
- **Native Dropdowns by Default**: Use native dropdown/select controls for fields that choose from a defined set of values: browser `<select>` on web and platform-native selection controls on iOS/Android. Use the same control type for equivalent fields. Do not replace these with custom modals, autocomplete or free-text inputs unless the user explicitly requests and documents that exception. Reuse existing native picker components where applicable.
- **Desktop Layouts**: Design every new screen for desktop windows (1200px and wider, `useIsWideLayout` in `src/theme/layout.ts`) as well as phones. List screens use `ListDetailLayout` (`src/components/ListDetailLayout.tsx`): the list on the left and the chosen item's view on the right, with the selection in a search param and arrow keys moving through the list. Top-level sections get an `AppSidebar` entry and a G-then-key shortcut in `KeyboardShortcuts`. Cover the desktop layout in the screen's E2E and visual tests; the `chromium` E2E project is already desktop-sized, so single-column flows call `useSingleColumnLayout(page)`.
- **Saved Filters**: Every filter remembers its last choice on the device, never synced with the profile. Hold a filter's state with `useSavedFilters` (`src/utils/savedFilters.ts`), never plain `useState`, and give each filter instance its own key: per profile for a profile-wide list (e.g. `treatments:<patientId>`), per resource for a filter on a resource's page (e.g. `condition-timeline:<conditionId>`). Pass a `parse` that drops saved options the filter no longer offers, wait for `isLoaded` before showing the filtered list, and cover a restart in the filter's E2E test.
- **Chosen Item Highlight**: On desktop, the item whose details show beside its list is marked with `SelectedRowMarker` (`src/components/SelectedRowMarker.tsx`), a bar along the row's left edge, plus `aria-current`, on every page. Never mark it by changing the row's background or text colour: rows keep their own background, e.g. a status wash. `ResourceRow` (`selected` appearance) and biomarker rows already do this.
- **Related Resources on View Pages**: When a view page shows resources related to the one being viewed (e.g. associated conditions, originating or linked consultations, treatments), render each group with the shared `ResourceSection` and `ResourceRow` components (`src/components/ResourceSection.tsx`) (the homepage lists conditions, consultations and treatments the same way, without cards): an icon and heading, then full-width rows with the resource title, a meta line (date, practitioner, status) and a chevron that opens the resource. Do not use cards, label/value rows or bespoke list styles for related resources. Leave out a related-resource section entirely when it has no resources: no empty headings and no "none yet" placeholder text (`ResourceSection` renders nothing without rows). Use each resource type's standard icon (`FolderPlus` for conditions, `Stethoscope` for consultations, `Pill` for treatments, `ClipboardList` for service requests).
- **Resource Links in Edit Forms**: Every resource's edit form MUST let the user establish and remove links to each related resource type, using `useLinkFields` and `LinkedResourcesField` (`src/components/`): one `+` menu option and one field per related type, with a native select on each link when it can be recorded in more than one way (e.g. a condition as a consultation's reason for visit or diagnosis). View pages never link or unlink: their `+` only starts creation forms for new related resources, and docks have no separate link button. When you add a resource type, add its link fields to the edit form of every resource it relates to, and theirs to its own.
- **Resource Meta Lines**: A resource's row (`ResourceRow`) and its view-page heading (`ResourceViewLayout` `meta`) MUST show the same meta line, built by one shared function per resource type (e.g. `getConditionMeta`, `getConsultationMeta`, `getTreatmentMeta`, `getServiceRequestMeta`) and rendered with `ResourceMetaLine`. Every meta item has its concept icon, and items are always ordered: date, status, specialist (if any), then resource-specific fields (e.g. service type, intent), then association counts on rows. Fields shown in the meta line are not repeated as label/value rows on the view page.
- **Relevant Icons**: Always give a relevant `lucide-react-native` icon to `+` menu options, related-resource section headings and metadata items, and reuse the same icon for the same concept everywhere. Never fall back to a generic icon (e.g. `FileText`) when a relevant one exists. Current mapping: conditions `FolderPlus`, consultations `Stethoscope`, treatments `Pill`, service requests `ClipboardList`, specialists and requesters `User`, service providers (organizations) `Hospital`, dosage `Tablets`, reasons `MessageSquareText`, notes `FileText`, dates `Calendar`, times `Clock`, status `CircleDot`, treatment and service request intent `Target`, planned dates `CalendarClock`, resolution dates `CalendarCheck`, instructions `ScrollText`, terminology codes `Hash`, severity and service type `Activity`, body site `MapPin`, verification `BadgeCheck`, category `Tag`, recovery phrase `KeyRound`, treatment regimens `Repeat`, quantity to dispense `Package`, regimen phases `Layers`, doses `Tablets`, amounts `Weight`, frequency (times) `Repeat2`, time of day `Clock`, route `Route`, course length `CalendarRange`, treatment logs and the journal `ListChecks`, lab results `FlaskConical`, the condition timeline `GitCommitVertical`, filters `ListFilter`, timeline step type `Shapes`, treatment usage `History`, offline `WifiOff`, start or resume taking `Play`, change usage `SlidersHorizontal`, regimen mismatch `TriangleAlert`, retry `RefreshCw`, duplicate `Copy`, treatment bundles `Group`, settings `Settings`, reorder `ArrowUpDown`, move up `ArrowUp`, move down `ArrowDown`, service request schedules (repeats) `Repeat2`, number of sessions `ListOrdered`, durations `Timer`, due windows `CalendarClock`, logged sessions `ListChecks`, increase `Plus`, decrease `Minus`, profile photo `ImagePlus`, switch profile `ArrowRightLeft`, Google Drive backup `Cloud`, show (reveal) `Eye`, export `Archive` with the `Download` action, copy to clipboard `Copy`, sync now `RefreshCw`, sign out `LogOut`, family name `Users`, gender `VenusAndMars`, privacy `ShieldCheck`, backup file `Archive` (as export), restore a profile `ArchiveRestore`, get started `ArrowRight`, import with AI `Sparkles`, paste from clipboard `ClipboardPaste`, calculated values `Calculator`, demo profile `Compass`. Extend this mapping when you add a concept.
- **Revealing Added Fields**: A field added from a form's `+` menu scrolls into view above the action dock and takes focus. Forms with a `+` menu get this by spreading `useFieldReveal().scrollViewProps` on their ScrollView and wrapping it and the `FloatingAddMenu` in `FieldRevealProvider` (`src/components/FieldReveal.tsx`); build added fields with `FormField` (and text inputs with `FormTextInput`) so they are revealed automatically.
- **Multi-line Text on View Pages**: Render every multi-line text field (notes, dosage instructions and any other text-area value) on a view page with the shared `ResourceTextSection` component (`src/components/ResourceTextSection.tsx`): a heading followed by plain body text. Never wrap such text in cards, borders or input-like boxes, and never give one text-area field a different treatment from the others.
- **Sync Change Capture**: Encrypted sync replicates clinical tables through SQLite triggers and a change log (`docs/adr/0001-local-first-sync.md`). Repositories never call sync code. When you add a FHIR resource table, add its capture triggers in a migration and register the type in `SYNC_RESOURCE_TYPES` and `RESOURCE_REGISTRY` (`src/features/sync/`) and its table in the upload subscription in `src/context/SyncContext.tsx`; deletions then sync automatically. Never write clinical rows with capture suppressed outside the sync engine.
- **Required and Optional Fields**: Mark every required form field with an asterisk (`FormField`'s `required` prop) — never forget it on a new field. Never write "(optional)" in a label: a field without an asterisk is optional. Optional fields stay hidden behind a `+` menu until added, and every visible optional field has an `x` (`FormField`'s `onRemove`) that clears it and returns it to the menu. Groups inside a field (e.g. regimen phases and doses) add their items and optional fields from a `+` next to the group heading, which opens the centered `AddOptionsModal`.
- **Form Field Attributes**: All form fields (`<TextInput>`, `<input>`, `<select>`, `<textarea>`) **MUST** have an `id` (or `nativeID`) and `name` attribute to prevent browser/accessibility warnings and ensure proper autofill and test targeting.
- **New Component Confirmation**: Always explicitly list and confirm in the plan if any new components need to be created, justifying why an existing component cannot be reused.
- **Database Migrations & Breaking Changes**: All database changes must have migrations, and migrations must be highlighted in the plan. You MUST explicitly highlight any breaking changes (or explicitly confirm that changes are non-breaking/additive).
- **Strict UI Scope**: Never add UI elements (badges, buttons, indicators, icons, labels, tags, etc.) that are not explicitly mentioned in the user request or approved implementation plan. Adhere strictly to the requested UI specifications and do not invent unsolicited visual elements.
- **Demo Profile**: The demo profile (`src/features/demo/demoProfile.ts`) is how new people first see Healthy, so it must always be presentable. When you add or change a feature, data field or screen, decide how the demo shows it: add realistic demo records that use the feature and update the ones it affects. Keep demo data consistent (logs follow schedules and start dates, statuses match dates, linked records point both ways) and dated relative to today, so it never looks stale. Before declaring a UI change done, open the screens it touches with the demo profile on a phone and on desktop and check they look complete: no empty sections, raw codes, placeholder text, long runs of missing logs or marks that read as failures. Keep `src/features/demo/demo-profile.e2e.ts` passing and extend it when the demo gains a feature.
- **GitHub Actions**: Pin every action to a full commit SHA with its version in a comment (`uses: actions/checkout@<sha> # v7.0.1`); Dependabot keeps the pins current. Give every workflow a top-level `permissions: contents: read` and grant more only on the job that needs it. CodeQL and OpenSSF Scorecard check both, and their alerts appear under Security › Code scanning: fix new ones in the change that adds them.
- **Git Staging & File Management**: Never stage (`git add`), unstage (`git restore --staged`, `git reset`), commit (`git commit`), or push (`git push`) any git files or changes in the branch unless explicitly asked by the user. Leave all modified files unstaged for the user to review. Cloud sessions are the exception: follow **Cloud sessions** below.

## Changelog and releases

- **Changelog Fragments**: You **MUST** update the changelog for every change users would notice — new features, fixes, behaviour or UI changes — in the same commit as the change, including follow-up changes pushed to an existing branch or pull request. Add a changie fragment: `pnpm changie new --interactive=false --kind <Added|Changed|Fixed|Removed|Security> --body "<entry>"`, one per change. Write the entry for the people using the app (what they can now do, what works better), not how it was built: no issue numbers, file names or internal terms. Changes users would not notice (refactors, tests, tooling, dependency bumps) need no fragment; if CI asks for one anyway, add a `Changelog: none` trailer to the commit message. Never edit `CHANGELOG.md` by hand; see `docs/releasing.md`.
- **Releases**: Merging a prepared release into `main` publishes its `v<version>` GitHub Release and deploys GitHub Pages and Play internal testing. Other merges and tag pushes alone publish nothing. Follow `docs/releasing.md`: prepare the next `YYYY.M.N` date version on a branch from `main` with `pnpm release:prepare`, then merge it. The workflow advances the internal `release` branch to trigger EAS; never advance it by hand. Never prepare, merge or publish a release unless the user asks for one.

## Cloud sessions

A cloud session (Claude Code on the web, the app or a GitHub integration) runs in a disposable container, so unpushed work is lost. When a cloud session works on a GitHub issue:

1. **Branch per issue, named as GitHub names it.** Branch from the latest `origin/main` and name the branch the way the issue's **Development → Create a branch** button does: `<issue-number>-<issue-title>`, lowercased, with every run of characters other than letters and digits replaced by one `-` and no leading or trailing `-` (issue #83 "PWA and offline indicator" → `83-pwa-and-offline-indicator`). Use this name even when the session assigned a different branch, and reuse the branch if it already exists.
2. **Commit and push** the finished, verified work to that branch (`git push -u origin <branch>`). This is the standing authorization the **Git Staging & File Management** rule otherwise requires.
   - **Update the branch before every commit.** First run `git fetch origin main <branch>`, bring in new commits on the remote branch (someone may have pushed or merged there), and merge `origin/main` when it has commits the branch lacks. Then verify and commit, so one push carries everything and CI runs once. Never push and then update the branch, which runs CI twice.
   - **Push rarely; CI minutes are limited.** Batch finished work into as few pushes as possible instead of pushing each commit. Never push while a CodeRabbit review of the pull request is running: wait for it to finish, address its findings in a separate commit, and push that together with any other local commits in one push.
3. **Attach it to the issue and its project.** A branch name alone does not show under the issue's **Development** section. Open a draft pull request from the branch whose body starts with `Closes #<issue-number>`: GitHub then lists it under the issue's **Development** section. Mark it ready for review only when the user asks.

## FHIR database standard

All database structures MUST follow HL7 FHIR R5 (v5.0.0). Persist clinical records as standard FHIR R5 resources using `fhir/r5` types. Relational columns, indexes and relationship tables are projections of those resources, not independent clinical schemas. Use standard FHIR elements, cardinalities, choice types, terminology bindings and references; never introduce custom clinical properties into resource JSON. Preserve valid fields that an editing form does not expose. App settings, sync metadata and storage timestamps are application infrastructure, not clinical FHIR resources.

## Local implementation plans

- Store implementation plans only in the local `.agents/plans/` directory. Treat them as local working artifacts.
- Never stage, commit, force-add, or publish `.agents/plans/` files. The directory must remain ignored by Git.
- When implementation and its required verification are complete, delete the implemented plan from `.agents/plans/`. Retain unfinished plans and update any local plan index to remove stale links.
- Put durable architecture, migration and recovery documentation outside `.agents/plans/`; those documents may be committed under the normal Git authorization rules.
